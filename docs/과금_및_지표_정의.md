## 0. 왜 기획서 숫자를 갈아엎었나

기획서 6.2는 크레딧 단가를 **"원가의 3~5배"** 로 정하라고 했다. 실제 원가를 계산해 보니
그 규칙이 성립하지 않는다.

| 액션 | 추정 토큰 (입력→출력) | 원가 |
|---|---|---|
| AI 종합 진단 리포트 | 10,000 → 3,500 | **약 29원** |
| 채널 1개 심층 분석 | 6,000 → 2,000 | **약 17원** |
| 컨설턴트 질문 1회 | 3,000 → 800 | **약 7원** |

(Gemini 3.7 Flash 도입가 `$0.75` / `$3.75` per 1M tokens, 1 USD ≈ 1,400원 기준.
도입가는 **2026-12-31까지**이고 2027-01-01부터 정가로 **2배**가 된다.)

기획서의 "리포트 10크레딧 = 1,000원"은 원가의 **34배**다. 3~5배가 아니다.

**결론: AI 원가는 가격을 결정할 근거가 못 된다.** 무시할 수준이라서, 남는 질문은
"이 리포트가 그 값을 하는가"뿐이다. 가격은 원가가 아니라 **가치와 심리적 저항**을 기준으로 정한다.

### 진짜 원가는 YouTube quota다

| | AI 분석 | YouTube Data API quota |
|---|---|---|
| 비용 성격 | 사용량 비례, 매우 저렴 | **일 10,000 units 고정 상한** |
| 돈으로 해결? | 됨 | **안 됨** (증량은 Google 심사) |
| 늘어나는 축 | 분석 횟수 | **연동 채널 수** |

댓글 동기화가 quota를 제일 많이 먹는다(영상 1개당 `commentThreads.list` 1 unit).
영상 500개 채널 한 번 풀 동기화에 500+ units.

**그래서 요금제에서 제일 중요한 줄은 "월 리포트 N회"가 아니라 "연동 채널 N개"다.**
기획서는 이걸 부수적으로 적었지만, 실제로는 이것이 유일한 고정 원가 통제 수단이다.

## 1. 요금제 — Free + Plus 2단계

기획서의 Free / Pro / Business 3단계를 **2단계로 축소**한다. 팀 시트·Business 티어는
수요가 확인되기 전까지 만들지 않는다.

| | **Free** | **Plus** |
|---|---|---|
| **가격** | 0원 | **₩4,900 / 월** |
| 연 결제 | — | **₩149,000 / 년** (10개월 가격) |
| **연동 채널** | **2** | **5** |
| AI 종합 리포트 | **0** (Plus 전용) | 월 3 |
| 채널 심층 분석 | **0** (Plus 전용) | 무제한(계산, AI 아님) |
| AI 컨설턴트 질문 | **0** (Plus 전용) | 월 30 |
| 영상 문구 AI 초안 | **0** (Plus 전용) | 월 30 |

> **변경**: 위 표의 Free 리포트 1회·컨설턴트 5회는 폐기했다. AI 종합 진단과 1:1 컨설턴트는
> Plus 전용 기능으로 확정됐고(`src/server/ai.ts`의 `requirePlusUser`가 403으로 막는다),
> Free에 무료 체험분을 주면 잠금 자체가 무의미해진다. 한도 구현은 `src/server/usage.ts`.
| 지표 보관 | 30일 | 12개월 |
| 주간 자동 리포트 메일 | ✗ | ✓ |
| CSV 내보내기 | ✗ | ✓ |
| 크레딧 구매 | **✓ (가능)** | ✓ |

**₩4,900인 이유**: ₩14,900은 개인 크리에이터가 첫 달에 지르기엔 비쌌다. 진입 장벽을 낮추고
**더 쓰는 사람에게서 크레딧으로 회수한다.** 구독은 시작하기 쉬운 가격, 크레딧은 쓰는 만큼.

**가격을 1/3로 내렸으므로 할당량도 같이 내렸다.** 안 내리면 AI 원가 비율이 12% → 37%가 된다.
리포트 10 → 3, 질문 150 → 30, 초안 150 → 30. 이 계산은 `src/server/usage.test.ts`가 붙들고 있다.

**월 리포트 3회면 충분한 이유**: 지표 수집이 **일 1회 배치**라 하루에 두 번 리포트를 뽑아도
입력 데이터가 같다. 3회면 열흘에 한 번꼴이고, 더 필요하면 5크레딧으로 추가 생성할 수 있다.

### 마진 확인

Plus 사용자가 할당량을 **100% 소진**했을 때:

```
리포트   3회 × 29원 =    87원
질문    30회 ×  7원 =   210원
초안    30회 ×  7원 =   210원
                    ─────────
AI 원가 합계            507원   →  매출 4,900원의 10.3%
```

2027년 정가(2배)로 올라도 1,014원 = **21%**. 건전하다.
(심층 지표는 우리 DB에서 계산하므로 AI 원가가 0이다. 그래서 Plus에서 횟수를 세지 않는다.)

## 2. 크레딧

**1 크레딧 ≈ 100원** 기준은 유지한다. **소모량을 기획서보다 낮춘다.**

| 액션 | 기획서 | **확정** |
|---|---|---|
| AI 종합 진단 리포트 | 10 | **5** |
| 채널 1개 심층 분석 | 3 | **2** |
| AI 컨설턴트 질문 1회 | 1 | **1** |

**낮춘 이유**: 가격을 내리려는 게 아니라 **"한 번 눌러보기 아깝다"는 저항을 없애기 위해서다.**
크레딧 제품에서 첫 사용을 막는 건 팩 가격이 아니라 클릭 한 번의 체감 비용이다.
스타터팩 기준 리포트 3회 → **6회**로 바뀌는데, 마진은 여전히 28배 이상이라 잃는 게 없다.

### 크레딧 팩 (기획서 유지, 구독 없이 누구나 구매)

| 팩 | 크레딧 | 가격 | 크레딧당 | 리포트 환산 |
|---|---|---|---|---|
| 스타터 | 30 | ₩4,900 | 163원 | 6회 |
| 스탠다드 | 100 | ₩14,900 | 149원 | 20회 |
| 벌크 | 300 | ₩39,900 | 133원 | 60회 |

### 차감 규칙

기획서 6.4를 그대로 따른다.

```
분석 요청
  ├─ 1. 구독 할당량 남았나?  → YES: quota_usage.used += 1, 크레딧 차감 없음
  ├─ 2. 크레딧 잔액 충분한가? → YES: credit_ledger에 차감 기록
  └─ 3. 402 Payment Required + 부족분 + 구매 링크
```

- 구독 할당량과 구매 크레딧은 **별도 잔액**. UI에 합산 표시하지 않는다
- 할당량 먼저 소진, 그다음 크레딧 (할당량은 이월 안 되므로 사용자에게 유리한 순서)
- 할당량은 결제 주기마다 리셋, **이월 없음**
- 구매 크레딧은 이월되고 **유효기간 구매일로부터 12개월**
- **Free 플랜도 크레딧을 살 수 있다** — 구독 없이 단발 결제가 가능해야 한다
- 환불: 미사용 크레딧은 구매 후 7일 이내 전액. 1개라도 썼으면 사용분 정가 차감 후 환불

### 원장 — MVP는 "성공 시 차감"으로 시작

기획서 6.5의 **홀드 → 커밋/릴리즈 3단계를 MVP에서 쓰지 않는다.**

그 설계는 AI 호출 실패로 돈만 빠지는 사고를 막으려는 것인데, **성공한 뒤에만 차감하면
그 사고가 애초에 발생하지 않는다.** 원장 상태가 절반으로 줄고 구현이 크게 짧아진다.

- **잃는 것**: 같은 유저가 동시에 여러 건을 던지면 잔액보다 더 쓸 수 있다
- **그 손해의 크기**: 건당 29원
- **그래도 유지할 것**: `pg_advisory_xact_lock(user_id)` 동시성 락, `Idempotency-Key` 유니크 제약,
  **append-only 원장 구조**(잔액 컬럼 직접 UPDATE 금지)

원장을 append-only로 두면 나중에 홀드/커밋을 얹을 수 있다. 거래량이 커지거나 원가가
올라가면 그때 도입한다.

## 3. AI 모델

**`gemini-3.7-flash` 하나로 통일한다.** 리포트·심층 분석·컨설턴트 전부 같은 모델.

**왜 컨설턴트를 더 싼 모델로 안 내리나**: Flash-Lite로 내려서 아끼는 돈이 질문당 몇 원이다.
모델을 둘로 나누면 프롬프트·스키마·품질 비교를 두 벌 관리해야 하는데, 그 관리 비용이
절감액보다 크다. **단일 모델이 더 싸다.**

### 코드에서 반드시 고칠 것

| 지금 (`server.ts`) | 고칠 것 |
|---|---|
| 모델명 `"gemini-3.7-flash"` 하드코딩, 2곳 중복 | 상수 1개 → `GEMINI_MODEL` 환경변수 (기본값 `gemini-3.7-flash`) |
| `responseMimeType: "application/json"` 만 지정 | **`responseSchema` 강제** + 응답 **Zod 검증** |
| `JSON.parse(text)` 무방비 | 검증 실패 시 **1회 재시도**, 두 번째도 실패하면 과금하지 않고 실패 처리 |
| 토큰 사용량 미기록 | **`usageMetadata`(입력/출력 토큰)를 `analysis_reports`에 저장** |
| 프롬프트/모델 버전 미기록 | 같이 저장 → 나중에 품질·원가 비교 가능 |

### 단가 재검토 조건

§0의 원가는 **프롬프트 크기 추정치**다. 실제 설계에 따라 3배까지 틀릴 수 있다.
`usageMetadata` 로깅을 붙이고 **2주간 실측한 뒤** 이 문서의 숫자를 갱신한다.

**재검토 트리거**:
- 실측 원가가 추정의 3배를 넘을 때

- Plus 사용자 평균 AI 원가가 매출의 30%를 넘을 때

## 4. 리포트 캐시

**같은 날, 같은 입력 데이터로 다시 요청하면 저장된 리포트를 반환하고 과금하지 않는다.**

지표 수집이 일 1회 배치이므로 같은 날 두 번째 요청은 입력이 동일하다. 여기서 또 과금하면
사용자가 "돈 뜯긴다"고 느낀다. 원가가 29원이라 캐시로 잃는 것도 없다.

캐시 키: `(user_id, scope, 마지막 동기화 시각)`. 동기화가 새로 돌면 캐시가 자연히 무효화된다.

## 5. 지표 계산 정의

AI 분석 화면(`AIAnalysisModal`)의 모든 항목을 실제 데이터로 계산하는 공식. 목업
(`ENGAGEMENT_DEEP_METRICS`, `CONTENT_FORMAT_STATS`)을 이 정의로 대체한다.

### 5.0 공통 — 정규화 함수

여러 지표를 0~100 점수로 환산할 때 **전부 이 함수를 쓴다.** 지표마다 다른 곡선을 쓰면
점수 간 비교가 무의미해진다.

```
norm(value, ref) = clamp(0, 100, 50 + 25 × log2(value / ref))
```

| value / ref | 점수 |
|---|---|
| 0.25배 | 0 |
| 0.5배 | 25 |
| **1배 (기준)** | **50** |
| 2배 | 75 |
| 4배 이상 | 100 |

로그를 쓰는 이유: 조회수·도달 배수는 롱테일이라 선형 정규화하면 대박 영상 하나가
점수를 전부 100으로 밀어버린다.

`value <= 0`이면 0점. `ref`는 각 지표에서 정의하고, **전부 가정치이므로 데이터가 쌓이면
채널 카테고리별로 재조정한다.**

### 5.1 기본 참여 지표

| 항목 | 공식 | 데이터 출처 | 상태 |
|---|---|---|---|
| `engagementRate` 참여율 | `(좋아요+댓글+공유) / 조회수 × 100` | `youtube_channel_daily_metrics` | ✅ 구현됨 |
| `shareRate` 공유율 | `공유 / 조회수 × 100` | 〃 | ✅ 수집 중 |
| `commentRatio` 댓글 비율 | `댓글 / 조회수 × 100` | 〃 | ✅ 수집 중 |
| `retentionRate` 시청 지속률 | `average_view_percentage` 조회수 가중평균 | 〃 | ✅ 수집 중 |
| `clickThroughRate` CTR | `impressions_click_through_rate` 조회수 가중평균 | 〃 | ⚠️ null 가능 → `–` 표시 |
| `topAudienceAge` 주 시청자 | `audience` 브레이크다운에서 조회수 1위 `ageGroup` + 비중 | `youtube_analytics_breakdowns` | ✅ 수집 중 |
| `saveRate` 저장율 | `videosAddedToPlaylists / 조회수 × 100` | **수집 추가 필요** | 🔧 |

> **`saveRate` 수집 추가**: YouTube에 "저장"이라는 지표는 없지만 **`videosAddedToPlaylists`**
> (나중에 볼 동영상 포함, 재생목록 추가 횟수)가 같은 의미다. 채널 일별 지표 요청의 metrics에
> 이 항목을 추가하고 컬럼 하나를 늘리면 된다.

**가중평균을 쓰는 이유**: 지속률·CTR을 날짜별 단순평균 내면 조회수 10회인 날과 10,000회인
날이 같은 무게를 갖는다. 반드시 조회수로 가중한다.

### 5.2 `viralityScore` — 바이럴 점수 (신규 정의)

**정의: 콘텐츠가 기존 구독자 밖으로 얼마나 퍼졌는가.**
구독자에게만 잘 보이는 채널은 바이럴이 아니다. 그래서 **비구독자 유입 비중**에 큰 가중치를 둔다.

**구성 요소** (선택 기간 합계 기준)

| 기호 | 지표 | 계산 | 기준값 `ref` |
|---|---|---|---|
| **R** | 도달 배수 | `기간 조회수 / 구독자 수` | `0.5` |
| **E** | 참여율 | `(좋아요+댓글+공유) / 조회수 × 100` | `5` (%) |
| **N** | 비구독자 시청 비중 | `비구독자 조회수 / 전체 조회수 × 100` | `50` (%) |
| **S** | 공유율 | `공유 / 조회수 × 1000` | `2` (‰) |

**N의 출처**: `subscribed_status` 브레이크다운이 **이미 수집되고 있다**
(`dimensions: "day,subscribedStatus"`). 추가 수집 없이 바로 쓸 수 있다.

**최종 점수**

```
viralityScore = round(
    0.35 × norm(R, 0.5)
  + 0.30 × norm(N, 50)
  + 0.20 × norm(E, 5)
  + 0.15 × norm(S, 2)
)
```

**가중치 근거**: 바이럴의 정의가 "구독자 밖으로 퍼짐"이므로 도달 배수(R)와 비구독자 유입(N)이
합쳐서 65%. 참여율(E)과 공유율(S)은 그 결과를 뒷받침하는 보조 지표다.

**예외 처리**

- **구독자 10명 미만**: R이 발산한다 → **R을 빼고** 나머지 가중치를 재정규화
  (`N 0.46 / E 0.31 / S 0.23`)
- **기간 조회수 0**: 점수를 내지 않고 **"데이터 부족"** 표시
- **`subscribed_status` 데이터 없음**: N을 빼고 재정규화 (`R 0.50 / E 0.29 / S 0.21`)

**공식을 UI에 공개한다.** 근거 없는 점수는 목업과 다를 게 없다. 점수 옆에 구성 요소
4개의 실제 값을 같이 보여준다.

### 5.3 `peakTime` — 업로드 시간대별 반응률 (신규 정의)

> ⚠️ **YouTube Analytics API에는 시간(hour) 디멘션이 없다.** `day` / `month`뿐이다.
> 그래서 "시청자가 접속하는 시간"은 **가져올 수 없다.** 대신 **우리 DB에 쌓인 이 채널의
> 업로드 이력으로 직접 집계한다.**

**측정 대상**: "이 채널이 그 시간대에 올렸을 때 실제로 잘 됐는가"

#### 영상별 초기 성과

발행 시점이 제각각이라 총 조회수로 비교하면 오래된 영상이 무조건 유리하다. **발행 직후
고정 기간으로 정규화한다.**

```
초기성과(v) = SUM(youtube_video_daily_metrics.views)
              WHERE metric_date BETWEEN 발행일 AND 발행일 + 2   -- 발행일 포함 3일
```

`youtube_video_daily_metrics`에 영상별·일별 조회수가 이미 쌓이므로 추가 수집 없이 계산된다.

**발행 후 3일이 안 지난 영상은 집계에서 제외한다.**

#### 슬롯 나누기

`source_published_at`을 **KST(Asia/Seoul)** 로 변환해 시간대 구간에 넣는다.

```
새벽 00–06 / 오전 06–12 / 오후 12–18 / 저녁 18–24
```

24개 구간으로 쪼개지 않는 이유: 영상 16개짜리 채널이면 구간당 0.7개다. 통계가 아니라 노이즈다.

**2단계 집계**:
- 기본은 **시간대 4구간만** (요일 무시)
- 영상이 **28개 이상** 쌓이면 **요일 × 시간대** (7×4 = 28슬롯)로 확장

#### 점수

```
slotScore(slot) = median(초기성과 of slot) / median(초기성과 of 전체)
```

**중앙값을 쓰는 이유**: 대박 영상 하나가 슬롯 하나를 통째로 왜곡한다. 표본이 적을수록 치명적이다.

#### 최소 표본 규칙 — 이게 제일 중요하다

```
전체 영상 12개 미만            → "데이터 부족" 표시, 추천하지 않음
해당 슬롯 영상 3개 미만        → 그 슬롯은 순위에서 제외
```

**표본 수를 반드시 화면에 같이 표시한다.**

```
저녁 18–24시 · 채널 평균의 1.8배 · 영상 7개 기준
```

표본 수 없이 "오후 8시가 최적입니다"라고 쓰면 그건 목업과 똑같은 거짓말이다.

#### 문구 주의

이건 **상관이지 인과가 아니다.** 그 시간에 올린 영상이 마침 주제가 좋았을 수도 있다.
UI 문구는 "이 시간대에 올린 영상이 평균보다 잘 됐습니다"여야 하고,
"이 시간에 올리세요"라고 단정하면 안 된다.

### 5.4 `bestFormat` / `CONTENT_FORMAT_STATS` — 포맷별 효율

**포맷 분류** (`youtube_videos` 기준)

| 포맷 | 조건 |
|---|---|
| 라이브 | `live_broadcast_content` 가 `none`이 아님 |
| 쇼츠 | `duration_seconds <= 180` |
| 미들폼 | `180 < duration_seconds <= 600` |
| 롱폼 | `duration_seconds > 600` |

**포맷별 집계** (5.3의 초기성과 정의를 재사용)

| 항목 | 공식 |
|---|---|
| `avgViews` | 포맷 내 초기성과 **중앙값** |
| `avgEngagement` | `(좋아요+댓글+공유) / 조회수 × 100`, 포맷 합계 기준 |
| `avgSavesOrShares` | 영상별 `shares` 중앙값 — **`video` 디멘션 브레이크다운 수집 필요** 🔧 |
| `efficiencyScore` | `norm(포맷 중앙값 / 채널 전체 중앙값, 1)` |
| `trend` | 직전 동일 기간 대비 `efficiencyScore` 변화. ±5점 이내면 `stable` |

**`bestFormat`** = `efficiencyScore`가 가장 높은 포맷. **표본 3개 미만 포맷은 후보에서 제외.**
전 포맷이 3개 미만이면 "데이터 부족".

### 5.5 요약 — 추가 수집이 필요한 항목

친구가 수집 구조를 맡으므로, 위 정의 중 **새로 받아와야 하는 것만** 추린다.

| # | 필요한 것 | 어디에 | 쓰이는 곳 |
|---|---|---|---|
| 1 | `videosAddedToPlaylists` 지표 | 채널 일별 지표 요청 metrics + 컬럼 1개 | `saveRate` |
| 2 | `video` 디멘션 브레이크다운 (`shares` 포함) | 신규 브레이크다운 리포트 | `avgSavesOrShares` |

**나머지는 전부 이미 수집 중인 데이터로 계산된다.** 특히 `viralityScore`의 핵심인
`subscribed_status`와 `peakTime`의 `youtube_video_daily_metrics`는 이미 있다.
