## 1. 제품 개요

### 1.1 한 줄 정의

유튜브 · 인스타그램 · 쓰레드 · X(트위터) 채널의 지표를 한 화면에 모으고, **AI가 채널별 개선 처방을 내주는** SNS 통합 관리 대시보드.

### 1.2 풀려는 문제

멀티 채널을 운영하는 크리에이터·마케터는 지금 이렇게 일한다.

- 채널마다 각각의 스튜디오/인사이트 화면에 따로 로그인해서 숫자를 본다
- 채널 간 비교가 안 된다 (유튜브 조회수와 쓰레드 노출수는 단위가 다름)
- "그래서 뭘 해야 하는지"는 아무도 안 알려준다. 숫자만 보여준다

우리가 파는 건 **숫자 집계가 아니라 처방**이다. 집계는 진입 조건이고, 돈을 받는 지점은 AI 분석이다. 이 구분이 뒤에 나오는 과금 설계 전체를 결정한다.

### 1.3 타깃

| 구분 | 설명 | 결제 성향 |
|---|---|---|
| 개인 크리에이터 | 1인 운영, 채널 2~4개 | 구독 부담 → **크레딧 단발 구매** 주력 |
| 마케팅 팀 | 브랜드 계정 대행 | 월 정액 구독 |
| 기업 | 브랜드 & 커머스 | 구독 + 팀 시트 |

온보딩 1단계에서 이 셋을 고르게 되어 있고(`OnboardingHero`), 현재는 대시보드 상단 배지에만 쓰인다. 나중에 티어 추천·기본 지표 구성에 연결할 자리다.

## 2. 현재 상태 — 뭐가 진짜고 뭐가 가짜인가

제일 먼저 알아야 하는 것.

### 2.1 진짜로 동작하는 것

- 온보딩 3단계 플로우 (관리 주체 → 플랫폼 선택 → 계정 등록)
- 대시보드 전체 렌더링, 채널 필터, Recharts 차트
- AI 분석 모달 3탭 (참여율 지표 / 종합 진단 / 1:1 컨설턴트)
- 글 작성 모달 → 작성한 글이 "최근 발행 콘텐츠"에 뜸 (**로컬 state에만**, 새로고침하면 사라짐)
- 회원가입 비밀번호 규칙 검증 (8자 이상 + 특수문자) — `src/passwordPolicy.ts`, 단위 테스트 있음
- `POST /api/gemini/analyze`, `POST /api/gemini/advisor` — `GEMINI_API_KEY`가 있으면 실제 Gemini 호출, 없으면 하드코딩 폴백 응답
- YouTube 채널 연동(OAuth, 채널·영상·분석·댓글 동기화)에 더해 영상 제목/설명 수정·삭제, 댓글 답글(대댓글)·숨기기·삭제까지 실제 YouTube API에 반영됨(`src/server/youtube.ts`, "원본 데이터" 페이지). 단 `youtube.force-ssl` 쓰기 권한이 도입되기 전에 연결된 채널은 재연결(재동의)해야 이 기능을 쓸 수 있음

## 3. 도메인 구성

### 3.1 웹 도메인 / 서브도메인

`laddersns.io`를 기준으로 잡는다 (**결정 필요**: 실제 취득 가능한 도메인 확인 후 확정. 코드 내 더미 이메일이 `@laddersns.io`로 통일되어 있음).

| 호스트 | 용도 | 비고 |
|---|---|---|
| `laddersns.io` | 랜딩 / 마케팅 | 정적, 공개 |
| `app.laddersns.io` | 제품 본체 (대시보드) | 로그인 필수 |
| `api.laddersns.io` | REST API | 프론트와 분리 |
| `docs.laddersns.io` | 개발/연동 문서 | 나중에 |

**왜 쪼개나**

- 랜딩과 앱을 나누면 랜딩을 CDN 정적 배포로 돌릴 수 있고, 앱 번들이 랜딩 속도를 깎지 않는다
- API를 별 호스트로 두면 쿠키 스코프와 CORS 경계가 명확해진다. 나중에 모바일/서드파티가 붙어도 그대로 쓴다
- OAuth 콜백 URL을 `api.` 아래로 고정하면, 프론트 배포 주소가 바뀌어도 각 플랫폼 개발자 콘솔에 등록한 리다이렉트 URI를 다시 안 건드려도 된다 ← 이게 실무에서 제일 아프다

**환경 분리**

```
prod     app.laddersns.io      api.laddersns.io
staging  stg.laddersns.io      api-stg.laddersns.io
local    localhost:3000        localhost:3000/api
```

각 플랫폼 개발자 앱은 **prod / staging을 별도 앱으로 등록**한다. 하나로 쓰면 스테이징 테스트가 프로덕션 quota를 갉아먹는다.

### 3.2 세션 쿠키 전략

`app.`과 `api.`가 서브도메인으로 갈리므로 쿠키 도메인을 `.laddersns.io`로 잡는다.

```
Set-Cookie: session=...; Domain=.laddersns.io; Secure; HttpOnly; SameSite=Lax; Path=/
```

`SameSite=Lax`면 OAuth 리다이렉트(외부 → 우리 도메인, top-level GET)에서 쿠키가 살아 돌아온다. `Strict`로 잡으면 콜백에서 세션이 끊긴다.

### 3.3 도메인 모델 (개념)

과금 도메인과 지표 도메인을 **분리**한다. 섞으면 나중에 못 푼다.

```
[계정 도메인]      User ─┬─ SocialAccount (플랫폼별 연동)
                        └─ Membership (팀, v2)

[지표 도메인]      SocialAccount ─┬─ MetricSnapshot (일별 집계)
                                  └─ Post ── PostMetric

[분석 도메인]      User ── AnalysisJob ── AnalysisReport

[과금 도메인]      User ─┬─ Subscription ── QuotaUsage
                        ├─ CreditLedger  (원장)
                        └─ Payment
```

핵심 경계: **분석 도메인은 과금 도메인에 "이만큼 쓸게" 라고 물어보기만 하고, 잔액 계산 로직은 전부 과금 도메인 안에 둔다.** 분석 코드 여기저기서 잔액을 직접 깎기 시작하면 정산이 깨진다.

## 4. 시스템 아키텍처

```
                    ┌──────────────────────────┐
    브라우저  ────▶  │ app.laddersns.io          │  React SPA (Vite 빌드 정적)
                    └──────────┬───────────────┘
                               │ fetch (쿠키 인증)
                    ┌──────────▼───────────────┐
                    │ api.laddersns.io          │  Node/Express
                    │  ├ /auth/*                │
                    │  ├ /connections/*         │  SNS OAuth
                    │  ├ /metrics/*             │
                    │  ├ /analysis/*            │  ← 과금 게이트
                    │  └ /billing/*             │
                    └───┬───────────┬───────┬───┘
                        │           │       │
              ┌─────────▼──┐  ┌─────▼────┐ ┌▼──────────────┐
              │ PostgreSQL │  │  Redis   │ │ 외부 API       │
              │            │  │ 큐/캐시  │ │ YouTube/IG/   │
              └────────────┘  └────┬─────┘ │ Threads/X     │
                                   │       │ Gemini        │
                            ┌──────▼─────┐ │ 결제 PG        │
                            │ Worker     │ └───────────────┘
                            │ 수집 배치   │
                            │ AI 분석 잡  │
                            └────────────┘
```

**왜 워커를 따로 두나**: SNS 지표 수집은 계정 수 × 플랫폼 수만큼 API 호출이 나가고, AI 리포트 1건은 수 초~수십 초 걸린다. HTTP 요청 안에서 처리하면 타임아웃과 중복 과금이 동시에 터진다. 분석은 **잡으로 던지고 폴링/SSE로 결과를 받는다.**

**결정 필요 — 배포처**

| 안 | 장점 | 단점 |
|---|---|---|
| Vercel(프론트) + Railway/Fly(API+워커) + Neon(PG) | 셋업 빠름, 관리 최소 | 비용이 트래픽 따라 급증 |
| 단일 VPS + Docker Compose | 월 2~3만원 고정 | 직접 운영 |
| Cloudflare Pages + Workers + D1/Hyperdrive | 엣지, 저렴 | 워커에서 장시간 잡 처리 제약 |

초기 사용자 수백 명 규모면 **2안(VPS)** 로 시작해도 충분하고 제일 싸다.

## 5. 데이터 모델

PostgreSQL 기준. 타입은 요약 표기.

### 5.1 계정

```sql
users (
  id              uuid pk,
  email           citext unique not null,
  password_hash   text,              -- 소셜 로그인만 쓰면 null
  name            text not null,
  user_type       text not null,     -- individual | team | enterprise
  created_at      timestamptz,
  deleted_at      timestamptz        -- soft delete (탈퇴 후 결제 이력 보존)
)

social_accounts (
  id              uuid pk,
  user_id         uuid fk → users,
  platform        text not null,     -- youtube | instagram | threads | x
  external_id     text not null,     -- 플랫폼 내부 채널/계정 ID
  handle          text not null,     -- @creativelab_kr
  access_token    bytea not null,    -- 암호화 저장 (5.4)
  refresh_token   bytea,
  token_expires_at timestamptz,
  scopes          text[],
  status          text not null,     -- active | expired | revoked
  connected_at    timestamptz,
  unique (platform, external_id)     -- 한 채널은 한 번만
)
```

`unique (platform, external_id)`가 중요하다. 이게 없으면 한 유튜브 채널을 여러 계정이 연동해서 지표를 중복 수집한다.

### 5.2 지표

```sql
metric_snapshots (
  id                uuid pk,
  social_account_id uuid fk,
  captured_on       date not null,   -- 일 단위
  followers         bigint,
  impressions       bigint,
  engagement_rate   numeric(5,2),
  posts_count       int,
  raw               jsonb,           -- 플랫폼 원본 응답 통째로
  unique (social_account_id, captured_on)
)

posts (
  id                uuid pk,
  social_account_id uuid fk,
  external_id       text not null,
  title             text,
  published_at      timestamptz,
  permalink         text,
  unique (social_account_id, external_id)
)

post_metrics (
  post_id      uuid fk,
  captured_on  date,
  views        bigint, likes bigint, comments bigint, shares bigint, saves bigint,
  primary key (post_id, captured_on)
)
```

**`raw jsonb`를 반드시 남겨라.** 플랫폼이 필드를 추가하거나 우리가 나중에 새 지표를 계산하고 싶을 때, 과거 데이터를 다시 못 받아온다. 원본을 쌓아두면 재계산으로 해결된다.

`unique (social_account_id, captured_on)`로 배치 재실행 시 멱등하게 upsert.

### 5.3 과금 (7장에서 상세)

```sql
subscriptions (
  id                   uuid pk,
  user_id              uuid fk,
  plan                 text not null,   -- free | pro | business

credit_ledger (
  id              bigserial pk,
  user_id         uuid fk,
  delta           int not null,      -- +충전 / -차감

  balance_after   int not null,
  ref_type        text,              -- analysis_job | payment
  ref_id          uuid,
  idempotency_key text unique,       -- ★ 중복 차감 방지
  expires_at      timestamptz,       -- 구매 크레딧 유효기간

payments (
  id                  uuid pk,
  user_id             uuid fk,
  kind                text,   -- subscription | credit_pack
  amount              int,    -- 원 단위 정수. float 금지

  status              text,   -- pending|paid|failed|refunded
  provider            text,
  provider_payment_id text unique,
  created_at          timestamptz
)
```

### 5.4 토큰 암호화

SNS 액세스 토큰은 평문 저장 금지. PG `pgcrypto` 또는 앱 레벨 AES-256-GCM.

```
KMS/환경변수의 마스터 키 → 컬럼 암호화
로그·에러 리포팅에 토큰이 절대 안 찍히도록 직렬화 시 마스킹
```

## 6. 과금 설계 ★

**이 서비스의 핵심 요구사항: 지표 분석은 구독으로도 되고, 크레딧을 사서 단발로도 된다.**

### 6.1 무엇이 유료인가

원가가 실제로 발생하는 지점에만 과금한다.

| 기능 | 원가 | 과금 |
|---|---|---|
| 채널 연동 | 없음 | **무료** |
| 기본 대시보드 (팔로워/노출/참여율/차트) | SNS API 호출 (거의 공짜) | **무료** |
| 최근 게시물 목록 | SNS API | **무료** |
| **AI 종합 진단 리포트** | Gemini 롱 프롬프트 + JSON 출력 | **유료** |
| **채널별 심층 분석** | Gemini | **유료** |
| **AI 1:1 컨설턴트 (질문 1회)** | Gemini 대화 | **유료** |
| 주간 자동 리포트 메일 | Gemini × 4회/월 | **구독 전용** |

기본 지표를 무료로 푸는 이유: 이게 잠겨 있으면 아무도 채널을 연동 안 한다. 연동 안 하면 분석을 팔 대상 자체가 안 생긴다.

### 6.2 크레딧 단가

### 6.4 차감 규칙 — 구독과 크레딧이 공존하는 방식

**이 절이 이 문서에서 제일 중요하다.** 여기가 틀어지면 정산 문의가 폭발한다.

```
분석 요청 들어옴
   │
   ├─ 1. 구독 할당량(quota)이 남았나?
   │      YES → quota_usage.used += 1  … 크레딧 차감 없음, 끝
   │      NO  ↓
   │
   ├─ 2. 구매 크레딧 잔액이 충분한가?
   │      YES → credit_ledger에 -N 기록
   │      NO  ↓
   │
   └─ 3. 402 Payment Required + 부족분/구매 링크 반환
```

**확정 규칙**

1. **구독 할당량과 구매 크레딧은 별도 잔액이다.** 합산해서 하나로 보여주지 않는다. UI에도 "이번 달 남은 리포트 3회 · 보유 크레딧 45" 로 따로 표기
2. **할당량 먼저 소진, 그다음 크레딧.** 사용자에게 유리한 순서 (할당량은 어차피 이월 안 되므로)
3. **구독 할당량은 결제 주기마다 리셋, 이월 없음.** `quota_usage`는 `period_start`로 파티션되므로 리셋은 새 행이 생기는 것뿐 — 배치가 필요 없다
4. **구매 크레딧은 이월된다. 유효기간 구매일로부터 12개월** (전자상거래법상 소멸시효 고지 필요)
5. **무료 플랜도 크레딧을 살 수 있다.** 구독 안 해도 단발 결제로 분석이 가능해야 한다 — 이게 요구사항의 핵심
6. **환불**: 미사용 크레딧은 구매 후 7일 이내 전액 환불. 1개라도 사용했으면 사용분 정가 차감 후 환불

### 6.5 원장(ledger)과 홀드/커밋

**잔액 컬럼을 직접 UPDATE 하지 마라.** `users.credits -= 10` 방식은 동시 요청에서 깨지고, 사고 났을 때 복구가 불가능하다. 대신 거래를 append 하고 잔액은 마지막 행의 `balance_after`를 읽는다.

AI 호출은 실패할 수 있으므로 **2단계 차감**을 쓴다.

```
① HOLD    분석 시작 전. delta = -10, kind='hold'
              → 잔액 즉시 감소 (동시에 두 번 못 쓰게)
② 성공 시  kind='commit' (delta = 0, 홀드 확정)
② 실패 시  kind='release', delta = +10  → 되돌림
```

```sql
-- 잔액 조회 (인덱스: user_id, id desc)
select coalesce((
  select balance_after from credit_ledger
  where user_id = $1 order by id desc limit 1
), 0);
```

**동시성**: 차감 트랜잭션은 `SELECT ... FOR UPDATE`로 유저 행을 잠그거나, `user_id` 기준 어드바이저리 락(`pg_advisory_xact_lock`)을 쓴다. 같은 유저가 탭 두 개에서 동시에 리포트를 누르는 건 실제로 자주 일어난다.

**멱등성**: 클라이언트가 요청마다 `Idempotency-Key` 헤더를 보내고, 서버는 `credit_ledger.idempotency_key` 유니크 제약으로 중복을 막는다. 네트워크 재시도로 두 번 깎이는 사고가 제일 흔하다.

### 6.6 결제 연동

**결정 필요**: 국내 사용자 대상이면 **토스페이먼츠**(카드·간편결제·자동결제 지원, 국내 정산). 해외까지면 Stripe.

주의할 것:

- **웹훅이 진실의 원천이다.** 클라이언트의 "결제 성공" 콜백을 믿고 크레딧을 지급하면 위조된다. 반드시 서버가 받은 웹훅에서 지급
- 웹훅은 중복 도착한다 → `payments.provider_payment_id` 유니크로 멱등 처리
- 구독 결제 실패(`past_due`) 시 즉시 차단하지 말고 유예 기간(3일)을 준다. 카드 한도 초과는 흔하고, 즉시 차단하면 이탈한다
- 금액은 **정수(원)** 로만 다룬다. float 쓰면 언젠가 1원이 어긋난다

## 7. SNS 플랫폼 연동 — 현실 확인 ⚠️

**여기가 이 프로젝트에서 제일 과소평가되는 부분이다.** 4개 플랫폼을 붙이는 건 UI 작업이 아니라 각각 별도의 심사·비용·제약이 있는 프로젝트 4개다. 착수 전에 반드시 각 플랫폼 최신 정책 문서를 직접 확인할 것 (아래는 작성 시점 기준이고, 이 바닥은 정책이 자주 바뀐다).

### 7.1 YouTube — 난이도 낮음

- **API**: YouTube Data API v3 (채널/영상 메타) + YouTube Analytics API (조회수·시청 지속시간 등 소유자 지표)
- **인증**: Google OAuth 2.0
- **비용**: 무료. 단 **일일 quota 10,000 units** — 호출당 units가 다르므로 배치 설계 시 계산 필요. 증량은 신청/심사
- **주의**: Analytics API는 채널 소유자 본인 인증이어야 나온다. 남의 채널 지표는 공개 데이터만

### 7.2 Instagram — 난이도 높음

- **API**: Instagram Graph API
- **전제 조건**: 대상 계정이 **비즈니스 또는 크리에이터 계정**이어야 하고, **Facebook 페이지와 연결**되어 있어야 한다. 개인 계정은 인사이트가 아예 안 나온다
- **인증**: Facebook 로그인 → 페이지 권한 → IG 계정 접근
- **앱 심사**: `instagram_basic`, `instagram_manage_insights` 등은 **App Review 필수**. 비즈니스 인증(사업자 등록증 등) 요구
- **현실**: 온보딩에서 사용자에게 "인스타 비즈니스 계정으로 전환 + 페이스북 페이지 연결"을 시켜야 한다. **여기서 이탈이 크게 난다.** 온보딩 UX에 이 안내를 반드시 넣어야 함

### 7.3 Threads — 난이도 중간

- **API**: Threads API (Meta). 비교적 최근에 열렸고 제공 지표가 제한적
- **인증**: Threads 전용 OAuth
- **주의**: 사용 가능한 인사이트 필드가 IG보다 적다. 지금 목업에 있는 "쓰레드 15분 티키타카 댓글" 같은 지표는 **API로 안 나올 가능성이 높다.** 실제 필드 목록을 먼저 확인하고 UI를 거기 맞춰야 한다

### 7.4 X (트위터) — 난이도 높음 + **비용 리스크** 🔴

- **API**: X API v2
- **비용**: 무료 티어는 사실상 쓸 수 없는 수준. **유료 티어가 월 수백 달러**부터 시작한다
- **이게 뭘 뜻하나**: 사용자가 몇 명이든 **X 하나 때문에 고정비가 발생**한다. Pro 구독 ₩19,900 기준으로 손익분기를 넘기려면 유료 사용자가 꽤 필요하다

**권고**:

1. v1은 **YouTube + Instagram + Threads 3개로 출시**하고 X는 "곧 지원" 배지로 둔다
2. X는 **Business 티어 전용 기능**으로 올려서 고정비를 상위 요금제가 부담하게 한다
3. 지금 코드는 이미 플랫폼별 필터가 `user.selectedPlatforms` 기반이라(`AIAnalysisModal`, `Dashboard`) 플랫폼을 빼도 UI가 깨지지 않는다 — 검증됨

### 7.5 공통 연동 규칙

- **토큰 만료 처리**: 리프레시 토큰으로 자동 갱신, 실패 시 `social_accounts.status = 'expired'` + 사용자에게 재연동 알림. 이 처리가 없으면 어느 날 조용히 지표가 멈춘다
- **레이트 리밋**: 플랫폼별 리밋을 워커에서 토큰 버킷으로 관리. 429 받으면 지수 백오프
- **수집 주기**: 지표는 실시간일 필요가 없다. **일 1회 배치(새벽)** 로 충분하고 quota도 아낀다. "실시간 연동 완료" 문구는 UI 카피일 뿐, 실제로는 일별 스냅샷

## 8. AI 분석 파이프라인

### 8.1 현재 구조의 문제

`server.ts`의 두 엔드포인트는 프로토타입용이다. 그대로 못 쓴다.

| 문제 | 수정 방향 |
|---|---|
| 인증 없음 — 누구나 호출 가능 | 세션 검사 미들웨어 |
| 과금 없음 | 6.4 차감 게이트 |
| 지표를 **클라이언트가 body로 보냄** (`platformStats`) | 서버가 DB에서 조회. 클라 입력을 믿으면 조작 가능 |
| 동기 호출 — 타임아웃 위험 | 잡 큐 + 폴링/SSE |
| 결과 저장 안 함 | `analysis_reports`에 저장, 재조회는 무료 |
| 모델명 하드코딩 | 상수/환경변수 |

### 8.2 목표 흐름

```
POST /api/analysis/report (Idempotency-Key)
   │
   ├─ 인증 확인
   ├─ 엔타이틀먼트 확인 → quota or credit HOLD      … 부족하면 402
   ├─ analysis_jobs INSERT (status=queued)
   └─ 202 { jobId } 반환
        │
     [워커]
        ├─ DB에서 해당 유저의 metric_snapshots 조회 (최근 30일)
        ├─ 프롬프트 구성 → Gemini 호출 (JSON 스키마 강제)
        ├─ 응답 검증 (Zod) — 스키마 안 맞으면 1회 재시도
        ├─ 성공 → analysis_reports 저장, ledger COMMIT, status=done
        └─ 실패 → ledger RELEASE (환불), status=failed
        │
GET /api/analysis/jobs/:id → { status, report? }
```

**중요**: 실패 시 반드시 크레딧을 되돌려라. AI 호출 실패로 돈만 빠지면 그 사용자는 안 돌아온다.

### 8.3 프롬프트/비용 관리

- 리포트 결과는 **캐시한다.** 같은 날 같은 데이터로 다시 요청하면 저장된 리포트를 무료로 반환. 지표가 바뀌지 않았는데 또 과금하면 안 된다
- 응답은 반드시 **JSON 스키마 강제 + Zod 검증**. 지금 코드는 `JSON.parse(text)`를 그냥 하고 있어서 모델이 마크다운 펜스를 붙이면 터진다
- 프롬프트/모델 버전을 `analysis_reports`에 같이 저장 → 나중에 품질 비교 가능
- 토큰 사용량을 로깅해서 **실제 원가**를 측정한다. 6.2 가격 확정의 근거가 된다

### 8.4 컨설턴트 탭

대화형이라 질문 1회당 1크레딧. 히스토리를 매번 전부 보내면 토큰이 선형 증가하므로 **최근 N턴 + 요약**으로 컨텍스트를 자른다.

## 13. 프론트엔드 실행 방법

```bash
npm install          # 또는 bun install
npm run dev          # http://localhost:3000
```

`GEMINI_API_KEY` 없이도 전부 돌아간다 (AI는 폴백 응답). 실제 Gemini를 붙이려면 프로젝트 루트에 `.env`:

```
GEMINI_API_KEY=...
```

기타 명령:

```bash
npm run lint         # tsc --noEmit (타입 검사)
npm run test         # 비밀번호 정책 단위 테스트
npm run build        # 프로덕션 빌드
```

자세한 건 `README.md` 참고.
